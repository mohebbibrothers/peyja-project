## ۱. gold-100 چیست و چرا؟

**gold-100** یعنی **«۱۰۰ نمونه‌ی طلایی»** — یعنی ۱۰۰ کپشنِ واقعیِ اینستاگرامِ فروشندگانِ
لوازم آرایشی، که **یک انسان** جوابِ درستِ هرکدام را کنارش نوشته. این «جوابِ کلید» (gold)
معیار سنجش موتور استخراج ماست:

```
کپشن خام  ──→  [ موتور استخراج پیجا ]  ──→  پاسخ موتور (prediction)
     │                                            │
     └──────────── مقایسه با کلیدِ طلایی ────────────┘
                        │
              نمره‌ها + حکم گیت‌ها
```

**چرا انسان؟** چون موتور هرچقدر هم خوب باشد، تا کسی جوابِ درست را نداند، «درستی» معنا
ندارد. گیتِ ما (قیمت ≥۸۵٪، دسته/ویژگی ≥۷۵٪) فقط وقتی معنا دارد که روی جواب‌های تأییدشده
سنجیده شود — و به همین دلیل شما فرمودید «نیازه توسط یه نفر چک بشه»؛ ابزار `gold-sheet`
دقیقاً همان برگه‌ی تأیید انسانی را می‌سازد.

### ساختار هر نمونه (samples.json)

| فیلد | معنا | مثال |
|---|---|---|
| `id` | شناسه‌ی نمونه | `gold-057` |
| `caption` | کپشن خامِ واقعی | «ریمل اسنس موجود شد ۵۵۰💸» |
| `price_toman` | قیمت فعلی به **تومان کامل** | `550000` |
| `old_price_toman` | قیمت خط‌خورده/قبلی | `null` |
| `category` | دسته‌ی غالب (۷ دسته) | `makeup` |
| `categories` | دسته‌ی چندگانه وقتی پست چند خانواده است («اسکین‌کر، آرایش») | `["skincare","makeup"]` |
| `brand` · `colors` · `shades` · `sizes` | برند/رنگ‌ها/شماره‌ی شید/سایز-حجم | `اسنس` · `[]` · `[]` · `[]` |
| `product_name` | نامِ محصول (کاتالوگی) — ممکن است فهرستِ جایگزین باشد | «کرم آبرسان» / `[«دورچشم»،«ابرسان»]` |
| `products` | فهرستِ «همه‌ی محصولات»ِ پست‌های چندمحصوله (نکته‌ی ۱) | `[{name, brand, category}…]` |
| `multi_product` | پستِ چندمحصوله (فهرستی یا بدونِ نام) | `true` |
| `volume_ml` · `spf` | مشخصه‌های عددی | `null` |
| `stock_state` | `in_stock` / `on_request` / `unknown` — **تا دورِ بعدی تأییدنشده** (نکته‌ی ۳) | `in_stock` |
| `synthetic` | نمونه‌ی مصنوعیِ پوششِ فرم؟ | فقط ۴ نمونه‌ی اول |
| `notes` | یادداشت برچسب‌زن | «سه‌رقمی = هزارتایی» |

### قواعدِ برچسب‌زنیِ طلایی («هر ایرانی چطور می‌خواند»)

1. **قیمت:** «۵۵۰💸» = ۵۵۰۰۰۰ تومان (سه‌رقمیِ بدون واحد = هزارتایی)؛ «۴/۸۰» = ۴٬۸۰۰٬۰۰۰
   (کسر ۲رقمی = صدم میلیون)؛ «حجم/وزن/ساعت/تعداد/شماره» **هرگز** قیمت نیستند؛
   اگر عددی در کار نیست = `null` — **حدس زدن ممنوع** (ضدِ توهم‌زایی).
2. **دسته:** دسته‌ی **خانواده‌ی غالبِ محصول**. توصیفگرهای عمومیِ فروشگاهی («لوازم آرایشی»،
   «لوازم بهداشتی»، «محصولات مراقبتی») به‌تنهایی تعیین‌کننده نیستند؛ اگر دو خانواده هم‌سطح
   بودند («آرایشی و پوستی») = `null`. پستِ صرفاً تعاملی/شوخی بدون محصول = `null`.
3. **ویژگی‌ها:** `colors` = تناژ/رنگ‌ها («صورتی و نود»)؛ `sizes` = شماره‌ی شید/سایز/حجمِ
   چسبیده به محصول («شماره ۱۷»، «۹۰ میل»).
4. **موجودی:** «موجود» ← `in_stock`؛ قیمت/موجودی پشت «دایرکت/کامنت/توافقی» ← `on_request`؛
   وگرنه `unknown`. ⚠️ **نکته‌ی ۳ (تأییدِ کاربر، دور ۲):** این ستون در برگه‌ی تأییدِ اول
   «دیده نشده» و تا تأییدِ دورِ بعدی **«تأییدنشده»** است. معنای دقیقِ سه حالت:

   | کدِ موتور | معنای فارسی | کجا استفاده می‌شود |
   |---|---|---|
   | `in_stock` | «موجود» — صراحتاً در کپشن/کامنت آمده | صفحه‌ی محصول، هشدارِ تمام‌شدن |
   | `on_request` | «استعلامی» — قیمت/موجودی با دایرکت/کامنت/«توافقی» | دکمه‌ی «استعلام در دایرکت» |
   | `unknown` | «نامشخص» — چیزی درباره‌ی موجودی گفته نشده | بدونِ ادعای موجودی (ضدِ اعتمادِ کاذب) |
   | `out_of_stock` | «ناموجود» — صراحتاً | فروخته‌شده/غیرفعال |

   هر مقدارِ موجودی هم مثل قیمت، «استخراج‌شده ≠ تأییدشده» است و Evidence دارد.

### چرا ۴ نمونه‌ی مصنوعی؟

فرم‌های سختِ قیمتِ فارسی («۴/۸۰»، «تخفیف از ۹۰۰ به ۷۵۰»، «توافقی») در کپشن‌های واقعیِ
این بچ **ظاهر نشدند**. این ۴ نمونه «پوششِ فرم» هستند: در `samples.json` با
`"synthetic": true` علامت‌گذاری شده‌اند و در نمره‌ها هم جدا گزارش می‌شوند
(`real_only` / `synthetic_only`) تا شفافیت کامل حفظ شود.

## ۲. موتور استخراج — «چه طور استخراج می‌کنیم؟» (spine-v0.2)

### لایه‌ها

```
رسانه/کپشن خام
   │
   ├─(الف) «موتور آفلاینِ فارسی» = price_parser + caption + CATEGORY_MAP   ← قلبِ gold-100
   │        قطعی، رایگان، آفلاین، قابل‌تست؛ همین = پیش‌بینیِ extract-text
   │
   └─(ب) «لایه‌ی VLM» (BoxApiAiProvider — هوش مصنوعی بکس‌اپی)
            فقط وقتی regex جا مانده/کم‌اعتماد است؛ خروجی با اسکیمای امن
            (SafeProductExtraction) + ۳ تلاش اصلاحی؛ هرگز خام نمی‌بلعد.
```

### الف) موتور آفلاین — قدم‌به‌قدم

**گام ۱ — نرمال‌سازی:** ارقام فارسی/عربی → لاتین، ZWNJ → فاصله، «_» هشتگ → فاصله،
تاشدنِ املایی (آ/أ→ا، ي/ى/ئ→ی، ك→ک، ة→ه + lowercase). «ابرسان» و «آبرسان» یکی می‌شوند.

**گام ۲ — قیمت (۷ قاعده‌ی price_parser):**

| # | قاعده | مثال | خروجی |
|---|---|---|---|
| 1 | کسرِ دو رقمی = صدم میلیون | «۴/۸۰» | ۴٬۸۰۰٬۰۰۰ |
| 2 | «X/YYY» = X میلیون + YYY هزار | «۴/۸۰۰» | ۴٬۸۰۰٬۰۰۰ |
| 3 | عددِ صریحِ «میلیون/هزار/تومان» | «۴ میلیون و ۸۰۰» | ۴٬۸۰۰٬۰۰۰ |
| 4 | سه‌رقمیِ بدون واحد = هزارتایی | «۴۸۰» | ۴۸۰٬۰۰۰ |
| 5 | تخفیف: «از X به Y» | «از ۹۰۰ به ۷۵۰» | old=۹۰۰k، new=۷۵۰k |
| 6 | on_request | «توافقی/دایرکت/تماس بگیرید» | price=null، stock=on_request |
| 7 | نگهبان‌ها | «حجم ۲۵۰mil»، «۲۴ ساعت» | **قیمت نیست** ✗ |

نگهبان‌های ضدِ‌توهم (درس‌های «عدد سرنوشت»):
- پسوندِ واحد (mil/میل/گرم/cc) بعد از عدد ⇒ حجم است نه قیمت («250mil»).
- واژه‌های «حجم/وزن/سایز/شماره/تعداد/ساعت/SPF» قبل از عدد ⇒ مشخصه است نه قیمت.
- «توافقی» بر حدسِ بدون واحد مقدم است؛ ولی عددِ صریحِ با واحد (conf 0.9) مقدم بر «توافقی».

**گام ۳ — ویژگی‌ها (caption.py):** ۲۳+ رنگ/تناژ (فارسی + لاتین: berry/burgundy/nude…)،
**شماره‌ی شید** (فیلدِ مستقلِ `shades`: «شماره ۱۲»، «کیکو ۱۷» — نه رنگ، نه سایز؛ با
نگهبانِ «۲۴ ساعت»/«۱۲ رنگ»/«۹۰ میل» و الزامِ لنگرِ آرایشی)، سایز/حجم («حجم ۵۰»، «۹۰ میل»)،
هشتگ‌ها.

**گام ۴ — دسته‌یابیِ دو لایه:**
1. **لایه‌ی محصول/برند (دقیق):** «کرم پودر»، «ضد آفتاب»، «پوست سر»، «bb کرم»، «ریمل»،
   «شیگلم»، «داو»… — **بلندترینِ چسبیده** برنده است («کرم پودر» بر «کرم»).
2. **لایه‌ی خانواده (اکثریت):** «پوست/پوستی»، «میکاپ/آرایش/آرایشی»، «بهداشتی» — با
   **شمارشِ رویارویی**؛ اکثریتِ قاطع برنده، تساوی = `null` («آرایشی و پوستی»).
- نگهبانِ مرزِ واژه برای کلیدهای کوتاه: «مداومه» حاوی «داو» نیست؛ «علاقه» حاوی «لاک» نیست.

**گام ۵ — ترکیب و مسیریابی (schema.py):**
- قیمت: regex پرقدرت (≥0.8) ← VLM ← regex ضعیف ← on_request؛ «echo فروشنده» در چت
  همیشه برنده‌ی نهایی (merge_seller_echo، conf 1.0).
- اعتماد ≥ 0.7 → `confirmed` (ذخیره‌ی خودکار) · 0.4–0.7 → `review` (نیازمند تأیید انسان)
  · < 0.4 → `reject`. محدوده‌های سلامت قیمت: 1٬۰۰۰ ≤ price ≤ 5٬۰۰۰٬۰۰۰٬۰۰۰ و old ≥ price.

### ب) لایه‌ی VLM (در pipeline کامل)

فقط وقتی regex قیمت نیاورد یا اعتماد < `extract_confidence_tau` باشد، کپشن به مدلِ
بینایی-زبانیِ بکس‌اپی می‌رود: **temperature=0** (تکرارپذیر)، حداکثر ۳ تلاش با
«خروجی قبلی نامعتبر بود — اصلاح کن»، و `SafeProductExtraction` (Pydantic) که خروجی را
ول می‌کند: title فارسی، category از واژگانِ بسته، قیمتِ محدوده‌دار، بدون null در میانه‌ی
لیست‌ها. نتیجه با regex ادغام می‌شود و شواهد (Evidence) با نام روش و اعتماد ثبت می‌شوند.

### مهندسیِ پرامپتِ VLM (قله‌ی تکنیک‌های روز)

`VLM_SYSTEM_PROMPT` با ساختارِ حرفه‌ایِ مهندسی پرامپت نوشته شده (تست‌شده در
`tests/test_prompt_engineering.py`):
1. **نقش (Role):** «استخراج‌گرِ متخصصِ بازارِ ایران» با دانشِ بومی.
2. **پروتکلِ گام‌به‌گام:** ترتیبِ استخراج (قیمت ← old ← دسته ← ویژگی ← موجودی).
3. **دانشِ بومیِ قیمت:** «X/YY»، سه‌رقمی=هزارتایی، «از X به Y»، «توافقی».
4. **دام‌ها (Negative knowledge):** «حجم 250mil»، «۲۴ ساعت»، «شماره ۱۲»، «۱۲ رنگ».
5. **Few-shot:** سه نمونه‌ی واقعیِ ورودی→خروجیِ JSON (شامل شید و on_request).
6. **قراردادِ خروجی:** فقط JSON مطابق اسکیما؛ لیست‌ها خالی ولی هرگز null.
7. **Self-check:** بازبینیِ خروجی در برابرِ دام‌ها پیش از پاسخِ نهایی.
8. **Retry دلیل‌دار:** پیامِ خطا با «دلیلِ» اعتبارسنجی (نه خطای خام).

### چرا دو موتور؟

regex «ستون فقرات» است: ارزان، سریع، قطعی، قابل‌تست — و برای **قیمت** (حساس‌ترین بخش)
همیشه اولویت دارد. VLM فقط گوشه‌های مبهم را پر می‌کند. این معماری «defense in depth»
جهانی است: هیچ لایه‌ای تنها تصمیم نمی‌گیرد؛ همه‌ی تصمیمات با `Evidence` ثبت و
قابل‌پیگیری‌اند (قانون ۴ — بازبینی انتقادی مستمر).

## ۳.۵ دور ۲ — تأیید انسانیِ بررس + ۴ نکته‌ی حیاتی

بررس، برگه‌ی ۶۴تایی را داوری کرد (JSON اصلاحاتِ ۱۶تایی + ۴ نکته). همه اعمال شد:

1. **پست‌های چندمحصوله** (gold-009/024/050/058 …): «همه‌ی محصولات» باید دربیاید، نه فقط
   یکی. موتورِ چندمحصوله (`catalog.split_product_spans` + `extract_multi_fa`): جداکننده‌های
   صریحِ فهرستی («۱.» «|» «؛» خط) ← مرزِ ایموجی بین دو متن ← مرزِ واژه‌ی محصولِ بعدی
   (با نگهبانِ «مرطوب کننده و ابرسان» = یک محصول). هر تکه، نام/برند/دسته/قیمتِ خودش
   را می‌گیرد. بازیابیِ محصولاتِ طلایی: **۱۰۰٪**.
2. **نامِ محصول** («کرم آبرسان» …): فیلدِ `product_name` در gold + استخراج در موتور
   (lexiconِ نام‌ها + امتیازِ «همسایگیِ برند»: «امپول کلاژن فارم استی» ← «امپول کلاژن»).
   برای کاتالوگ/جست‌وجو/دسته‌بندیِ دقیق‌تر. دقت: **۱۰۰٪** روی ۲۶ نمونه‌ی نام‌دار.
3. **موجودی تأییدنشده:** بررس ستونِ موجودی را ندیده — تا دورِ بعدی «تأییدنشده» است؛
   معنای هر کد در جدولِ بالا (نکته‌ی ۳) شفاف شد و در برگه‌ها هم درج شد.
4. **دسته‌ی «خوشبو کننده»:** به‌جای بهداشتیِ خام، دسته‌ی جدیدِ **`deo_fragrance`**
   (اسپری بدن/ضدتعریق/دئودورانت/مام/لوسیون بدن/خوشبوکننده/داو/**بادی اسپلش**) ساخته شد.
   ۶ برچسبِ «خوشبو کننده»ایِ کاربر (gold-018/020/037/058/063/064) همگی اکنون درست‌اند.
   ⚠️ **درسِ خطای انسانی:** «بادی اسپلش» ابتدا (در تأییدِ دور ۱) به‌اشتباه
   «بهداشتی» تأیید شد — با تصحیحِ کارفرما به `deo_fragrance` برگشت و **سپرِ
   سازگاریِ خانواده‌ای** (`consistency_report` در `evals.py`) ساخته شد تا هر تضادِ
   برچسبیِ متقاطع را قبل از نمره‌دهی فریاد بزند. «برچسبِ انسانی قابلِ احترام ولی
   قابلِ خطاست» — اکنون قانونِ ثبت‌شده در `PROJECT-LAWS.md` است.

**۳ خطای باقی‌مانده‌ی دسته** (gold-019/052/057): پست‌هایِ تعاملی/شوخیِ بدونِ محصول که
بررس برچسبِ `null` آن‌ها را «تأیید» کرده؛ موتور هنوز با خانواده‌ی هشتگی پر می‌کند —
این‌ها به‌عنوانِ خطای صادقانه‌ی موتور می‌مانند («استخراج‌شده ≠ تأییدشده») و سوژه‌ی
نسخه‌ی v0.3 («آیا اصلاً محصولی تبلیغ شده؟»).

## ۴. تکرارپذیری (دستورات از ریشه‌ی مخزن)

```bash
python evals/gold-100/build_batch1.py                      # ساخت samples.json
python -m peyja extract-text evals/gold-100/samples.json --out out/predictions.json
python -m peyja gold-score                                  # «عدد سرنوشت» + حکم گیت‌ها
python -m peyja gold-sheet                                  # برگه‌ی تأیید (md + html تعاملی)
python -m pytest                                            # شامل test_gold_regression = قفلِ کیفیت
```

**قفلِ کیفیت در CI:** `tests/test_gold_regression.py` در هر push موتور آفلاین را روی
gold-100 می‌دواند و گیت‌ها + کفِ نمره‌ها (قیمت ≥۰.۹۹ · دسته ≥۰.۹۴ · ویژگی ≥۰.۸۵ ·
بازیابیِ محصول ≥۰.۹۵ · نام ≥۰.۹۰ · برند ≥۰.۹۵) را می‌سنجد — «تا آخر تست و اصلاح»
حالا یک مکانیزمِ خودکار است، نه عادت.

## ۵. نقشه‌ی راهِ gold-100

- **بچ ۱ (۶۴ نمونه)** ✅ ساخته، برچسب‌خورده، **تأییدِ انسانیِ دور ۱ اعمال‌شده**،
  نمره‌خورده — برگه‌ی تعاملی برای دورِ بعدِ تأیید (ستونِ موجودی) آماده است.
- **بچ ۲ (۲۰–۳۰ نمونه‌ی پرفروش/قیمت‌دار):** از هشتگ‌های `#قیمت #موجودی #تخفیف`
  (Data API پس از تمدید اشتراک) — سهمِ «برچسب‌دارِ ویژگی/قیمت» باید بالا برود تا
  گیت‌ها سخت‌گیرانه‌تر شوند.
- **بچ ۳ (تا ۱۰۰):** تنوع فروشنده + فرم‌های باقی‌مانده («۲/۵»، «میلیون» صریح).
- پس از تأیید انسانی: گیت‌های gold-100 «رسمی» اعلام و در CI قفل می‌شوند.
